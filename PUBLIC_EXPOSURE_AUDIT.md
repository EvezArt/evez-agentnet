**Why this matters:** a `service_role` key **bypasses row-level security**.
Anyone holding it has unrestricted read/write on the entire database, regardless
of any RLS policies configured. This is categorically worse than an `anon` key,
which is designed to be publishable.

**Live status:** UNCONFIRMED.

  not a DNS failure — it is provisioned)

  deny key validity)

**Actions:**
1. **Rotate the key now.** Assume compromise regardless of the 522 — the key has
   been publicly readable since the commit, and GitHub indexes and caches.
2. Move it to an environment variable; commit only a placeholder.
3. Audit Supabase auth logs for unknown `service_role` usage since first push.
4. Bump the JWT `exp` (current claim: **2036-03-19** — a 10-year lifetime is
   far longer than necessary).

## FINDING 4 — committed virtualenvs

`evez-liminal` has `.venv/` committed (**113MB**), including
`.venv/lib/python3.12/site-packages/…`. This is not a leak, but it:
- inflates clone size for every consumer
- guarantees scanners flag third-party files as *your* exposure
- pins you to Python 3.12 exactly

**Fix:** add `.venv/` to `.gitignore`; `git rm -r --cached .venv`.

Related bloat in public repos: `evez-audio-packs` **411MB**, `evez-os` **133MB**,
`evez-liminal` **113MB**, `evez-ai` **79MB**, `evez-atlas` **64MB**.
